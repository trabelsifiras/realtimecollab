# Real-Time Collaboration Platform — Full Product & Engineering Specification

## 0. Document Purpose

This document is the authoritative specification for building a production-ready real-time collaboration web application.

The application is a SaaS-style collaboration platform where users can create or join workspaces, collaborate on projects, manage tasks, communicate through channels/chat, receive real-time notifications, see user presence, and eventually collaborate on documents.

The implementation must contain:

- Angular frontend
- Spring Boot backend
- PostgreSQL persistence
- WebSocket/STOMP real-time communication
- Spring Security + JWT authentication
- Role-based authorization
- Docker/Docker Compose development environment
- Automated tests
- API documentation
- Database migrations
- Clean modular architecture

The initial implementation MUST be a modular monolith rather than microservices. The architecture must nevertheless keep domain modules sufficiently isolated so they can later be extracted into services.

---

# 1. Product Vision

Build an application similar in spirit to a combination of:

- Slack: channels, messages, presence, notifications
- Jira/Trello: projects, tasks, statuses, assignments
- Notion: documents and collaborative content
- Microsoft Teams: workspace/team collaboration

The primary differentiator is real-time collaboration.

A user should be able to perform an action and other authorized users should see the result immediately without refreshing the browser.

Examples:

- User A changes a task status → User B sees it immediately.
- User A assigns a task → User B receives a notification.
- User A writes a chat message → other channel members receive it instantly.
- User A goes online → other workspace members see the presence update.
- User A starts typing → other participants see a typing indicator.
- User A comments on a task → the comment appears live for everyone viewing the task.

# 3. Architecture Principles

## 3.1 Start as a Modular Monolith

Do NOT start with microservices.

Backend structure:

```text
backend/
└── src/main/java/com/collab/
    ├── auth/
    ├── user/
    ├── workspace/
    ├── project/
    ├── task/
    ├── comment/
    ├── channel/
    ├── chat/
    ├── notification/
    ├── presence/
    ├── realtime/
    ├── file/
    ├── document/
    ├── common/
    └── config/
```

Each module should own:

- domain/entity model
- repository
- service
- controller
- DTOs
- validation
- module-specific events

Avoid a giant shared service layer.

## 3.2 Layering

Each module should generally follow:

```text
Controller
    ↓
Application Service
    ↓
Domain / Repository
    ↓
Database
```

Controllers must not contain business logic.

Entities should not be directly returned by REST APIs.

Use DTOs.

## 3.3 Domain Events

Important business actions should produce events.

Examples:

```text
TaskCreatedEvent
TaskUpdatedEvent
TaskAssignedEvent
CommentCreatedEvent
MessageCreatedEvent
UserJoinedWorkspaceEvent
NotificationCreatedEvent
UserPresenceChangedEvent
```

The real-time module converts relevant events into WebSocket messages.

# 4.6 Optimistic Locking

Tasks must support optimistic locking.

Use a version field:

```text
version
```

Example:

```text
User A reads task version 4
User B reads task version 4

User A updates → version 5

User B tries to update version 4

Backend rejects the update because version 4 is stale.
```

Return:

```text
409 CONFLICT
```

with a structured error:

```json
{
  "code": "RESOURCE_VERSION_CONFLICT",
  "message": "The task was modified by another user.",
  "resourceId": "123"
}
```

Frontend must handle this gracefully.

# 6. WebSocket Security

The WebSocket connection must be authenticated.

Do not trust client-supplied:

```text
userId
workspaceId
role
```

The server must derive identity from the authenticated security context.

Authorization must be performed for subscriptions and messages.

Example:

```text
User A connects
    ↓
Authenticated as userId=10
    ↓
Attempts to subscribe:
 /topic/workspaces/999
    ↓
Backend checks membership
    ↓
If not authorized:
 reject subscription
```

Never expose private workspace/channel events to unauthorized users.

# 8. REST vs WebSocket

REST is responsible for durable state.

WebSocket is responsible for real-time propagation.

Example:

```text
PATCH /tasks/123
       ↓
Persist task
       ↓
Generate event
       ↓
WebSocket broadcast
```

Do NOT use WebSocket as a replacement for all REST operations.

The database remains the source of truth.

A client must NOT be able to subscribe to arbitrary:

```text

/topic/channels/{id}
/topic/tasks/{id}
```

For every subscription, verify:

```text

        +

        +

```

# 25. Concurrency

The system must assume multiple users modify the same resources simultaneously.

Use:

- optimistic locking
- database transactions
- proper isolation
- deterministic ordering
- server timestamps

Example:

```text
Task version 10

User A → update
User B → update

Only one update against version 10 succeeds.
```

Frontend should display a meaningful conflict message and offer refresh/retry.

# 54. Offline/Reconnection Behavior

When WebSocket disconnects:

```text
CONNECTED
   ↓
DISCONNECTED
   ↓
RECONNECTING
   ↓
CONNECTED
```

Frontend should:

- show connection state
- reconnect automatically
- resubscribe
- refresh stale state when necessary
- avoid duplicating subscriptions
- avoid losing important durable actions

Never assume that an event missed during disconnection was received.

After reconnection, refresh relevant state from REST.

# 57. Data Consistency

The PostgreSQL database is the source of truth for durable business data.

WebSocket events are notifications of state changes, not the authoritative data store.

If a client is unsure about state:

```text
GET REST resource
```

rather than trying to reconstruct the entire state solely from WebSocket events.

# 61. Coding Agent Rules

The coding agent MUST follow these rules.

## Rule 1

Do not implement fake functionality.

If an endpoint is implemented, it must actually persist/read/update real data.

## Rule 2

Do not bypass authorization.

Every protected resource must verify ownership/membership/permission.

## Rule 3

Do not expose entities directly.

Use DTOs.

## Rule 4

Do not put business logic in controllers.

## Rule 5

Do not use `any` excessively in Angular.

Prefer strong TypeScript models.

## Rule 6

Do not duplicate WebSocket connections.

Use a centralized realtime service.

## Rule 7

Do not trust client user IDs.

Derive identity from authentication.

## Rule 8

Do not rely on frontend authorization.

Backend authorization is mandatory.

## Rule 9

Do not add Kafka/Redis/Kubernetes prematurely.

Implement the simplest architecture that satisfies the current requirements.

## Rule 10

Do not skip tests.

Every important business rule must have automated coverage.

## Rule 11

Do not leave TODO placeholders for core functionality.

## Rule 12

Keep the application runnable after every major phase.

# 65. Engineering Philosophy

The most important principle is:

```text
Simple first.
Correct second.
Real-time third.
Scale when needed.
```

The first version should be a clean modular monolith.

Do not create unnecessary distributed complexity.

However, all boundaries should be designed so that the following can be added later without rewriting the entire application:

```text
Redis
Kafka
multiple Spring instances
object storage
search engine
CRDT collaboration
Kubernetes
```

The application must prioritize:

```text
Security
Correctness
Maintainability
Real-time UX
Testability
Observability
Scalability
```

over premature architectural complexity.
